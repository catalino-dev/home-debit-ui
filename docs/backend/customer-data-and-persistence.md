# Customer data and persistence

## API fields

| Field | JSON type | Required | Constraints / meaning |
|---|---|---|---|
| `id` | number | Response only | Generated database ID. |
| `fullName` | string | Yes | Nonblank; stored in `full_name`, up to 255 characters. |
| `email` | string | Yes | Nonblank and valid email format; unique in the database, up to 255 characters. |
| `mobileNumber` | string | Yes | 7–15 digits; stored as a string to preserve leading zeroes. |
| `nickname` | string or `null` | No | Optional (US-03); ≤50 characters; blank or missing is stored as `null`. Always present in responses. |

`CustomerRegistrationRequest` validates inbound registration values and
`CustomerUpdateRequest` validates `PUT` updates with the same rules.
`CustomerResponse` is the response record and maps the JPA entity into API
fields. The frontend's `Customer` has three required `String` fields plus
nullable `int? id` (assigned by the backend) and `String? nickname`. The UI
sends the four editable fields (with `nickname: null` when not provided) and
reads the returned ID into the model.

## Persistence mapping

`Customer` maps to the `customer` table. Its `id` is generated with an
identity column. The repository extends `JpaRepository<Customer, Long>` and
adds lookup by email for the duplicate check. Profile updates go through
`Customer.updateProfile(...)` inside a `@Transactional` service method, so JPA
dirty checking writes the change on commit; the update's duplicate-email check
ignores the customer's own row.

## Schema migrations

Flyway migration `V1__create_customer_table.sql` creates:

| Column | Database type | Constraints |
|---|---|---|
| `id` | `BIGSERIAL` | Primary key |
| `full_name` | `VARCHAR(255)` | Not null |
| `email` | `VARCHAR(255)` | Not null; unique constraint `uk_customer_email` |
| `mobile_number` | `VARCHAR(15)` | Not null |
| `created_at` | `TIMESTAMP` | Not null; defaults to current timestamp |

`V2__add_customer_nickname.sql` (Week 2, US-03) adds:

| Column | Database type | Constraints |
|---|---|---|
| `nickname` | `VARCHAR(50)` | Nullable, no default — existing rows read as `null` ("not provided") |

JPA is configured with `ddl-auto: validate`; schema changes should be delivered
as Flyway migrations, not generated by Hibernate.

## Cross-project mapping

The UI and API share the JSON names `fullName`, `email`, `mobileNumber`, and
`nickname`. The backend response includes `id`; the UI's `Customer.fromJson`
maps it along with the profile fields. The profile screen displays name,
email, mobile number, and nickname (or `Not provided`), not the ID.
