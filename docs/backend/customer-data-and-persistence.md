# Customer data and persistence

## API fields

| Field | JSON type | Required | Constraints / meaning |
|---|---|---|---|
| `id` | number | Response only | Generated database ID. |
| `fullName` | string | Yes | Nonblank; stored in `full_name`, up to 255 characters. |
| `email` | string | Yes | Nonblank and valid email format; unique in the database, up to 255 characters. |
| `mobileNumber` | string | Yes | 7–15 digits; stored as a string to preserve leading zeroes. |

`CustomerRegistrationRequest` validates inbound registration values.
`CustomerResponse` is the response record and maps the JPA entity into API
fields. The frontend's `Customer` currently has the three profile strings but
also carries the backend-generated `id` on persisted responses. The UI sends
only the three registration fields; it reads the returned ID into the model.

## Persistence mapping

`Customer` maps to the `customer` table. Its `id` is generated with an
identity column. The repository extends `JpaRepository<Customer, Long>` and
adds lookup by email for the duplicate check.

## Schema migration

Flyway migration `V1__create_customer_table.sql` creates:

| Column | Database type | Constraints |
|---|---|---|
| `id` | `BIGSERIAL` | Primary key |
| `full_name` | `VARCHAR(255)` | Not null |
| `email` | `VARCHAR(255)` | Not null; unique constraint `uk_customer_email` |
| `mobile_number` | `VARCHAR(15)` | Not null |
| `created_at` | `TIMESTAMP` | Not null; defaults to current timestamp |

JPA is configured with `ddl-auto: validate`; schema changes should be delivered
as Flyway migrations, not generated by Hibernate.

## Cross-project mapping

The UI and API share the JSON names `fullName`, `email`, and `mobileNumber`.
The backend response includes `id`; the UI's `Customer.fromJson` maps it along
with the profile fields. The profile screen currently displays the name, email,
and mobile number, not the ID.
