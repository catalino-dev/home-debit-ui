US-03 · Concept

Null safety: say which values may be missing

The model says it, the compiler enforces it

class Customer {
  final int? id;            // null until the backend saves it
  final String fullName;     // always present
  final String email;
  final String mobileNumber;
  final String? nickname;   // US-03: optional
}

// Profile — fallback instead of a crash or "null"
value: _customer.nickname ?? 'Not provided',

Only genuinely optional data is nullable. The other three stay String, so the compiler stops anyone reading them as maybe-missing.

The four operators, in this codebase

?
String? — the type admits null. Used for nickname and id.
??
"if null, use this" — nickname ?? 'Not provided', and nickname ?? '' to seed the edit field.
!
"trust me, not null" — _formKey.currentState!. Throws if wrong, so used sparingly; we prefer type promotion.
late
"assigned before first read" — late Customer _customer set in initState; controllers are late final.

Blank input becomes null on both sides (nullIfBlank in Dart, normalizeNickname in Java), so there's one meaning of "no nickname".

setState

Only the owner calls it: Profile after a successful edit, Edit for loading/error. Typed text needs no setState — the controller notifies its field.

TextEditingController

Created once in initState from the current values, disposed in dispose(). Creating it in build would wipe the user's typing.

Navigation as a result

Navigator.push<Customer> returns Customer? — null safety forces Profile to handle "no result" (Cancel).

Live demo · 3 of 4 · the challenge question

What happens to unsaved changes?

draft
"Juan Draft" / "Unsaved" exist only inside Edit's controllers.
Cancel
Profile unchanged. No request was sent; DB row untouched.

They're gone — by design

  • Cancel (or back) → Navigator.pop(context) with no result
  • Edit's State is disposed → controllers disposed → draft discarded
  • Profile gets null, returns early, keeps _customer
  • Re-opening Edit starts again from the saved profile

Because the draft and the saved data live in different owners, discarding one can't corrupt the other.

Live demo · 4 of 4 · failure path

Save fails? Stay on Edit, keep the draft

HTTP 409
Email belongs to another customer. Error shown on Edit; nothing on Profile changes.

Rules the backend enforces

  • Keeping your own email → 200, not a conflict
  • Another customer's email → 409, record unchanged
  • Invalid fields → 400 · unknown ID → 404 ("register again")

Found in code review, fixed

Back during an in-flight Save could pop with null while the PUT still committed → stale Profile, and the next Save would silently revert it. Fix: PopScope(canPop: !_isSaving) + hidden back arrow — with a regression test.
